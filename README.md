# aep-outage-prediction

GridGuide: a Vite/React frontend with a Hono/Bun backend. It has three parts that share one codebase:

| Page | URL (dev) | What it is |
| --- | --- | --- |
| Network map | `/map.html` | Interactive GIS map of the distribution network, ARCOS damage, isolation planning and issue prioritization |
| Client chat | `/client.html` | Customer-facing chat over a satellite map: find your premise by address, check status, get an estimated restoration window, ask the LLM outage questions |

```bash
bun install
```

## Running

Copy `.env.example` to `.env` and set `GROQ_API_KEY` (the chat app and the client chat's free-text answers need it). Optionally set `GROQ_MODEL` (defaults to `llama-3.3-70b-versatile`), `PORT`, `DATABASE_PATH`.

```bash
bun run dev          # Vite (http://localhost:5173) + API server (port 3001)
bun run typecheck
bun run build        # builds both pages
bun run start        # production: built frontend + API on http://localhost:3001
bun test             # database tests
```

Vite proxies `/api` to the Hono server on port 3001. If you change `PORT`, update the proxy target in `vite.config.ts` too. The API key is only read by the backend; never prefix it with `VITE_`. The map page works without the API server except for the debug address lookup; the client chat needs it.

## Data setup

The map and client chat need the AEP shapefiles and a generated GIS dataset. Both are git-ignored (`data/`, `public/gis/`), so build them after cloning.

1. **Download** (needs `curl` and `unzip`):

   ```bash
   bun run data:pull    # or: bash scripts/download-data.sh
   ```

   Downloads the three ZIPs into `./data` and extracts `data/Data1/`, `data/Data2/` and `data/matched_upstream/`. Existing ZIPs are reused; extracted files are overwritten.

2. **Build the GIS dataset.** Needs a Python virtualenv at `.venv` with `pyshp` and `numpy`:

   ```bash
   python3 -m venv .venv && .venv/bin/pip install pyshp numpy
   bun run gis:build
   ```

   `gis:build` runs two scripts:
   - `scripts/build-gis.py` merges Data1 + Data2 into GeoJSON under `public/gis/` (primary/secondary conductors, poles, transformers, fuses, switches, reclosers, ARCOS damage, hospitals, fire stations, ambulance, anonymized customers), plus `chains.json`/`topology.json`/`anchors.json` from `matched_upstream.txt`, and a private address index at `data/premise-addresses.json`.
   - `scripts/build-isolation.py` adds an isolation point to every ARCOS report (see below) and writes `opendown.json`.

   Premise pseudo-IDs use a random salt, so **every rebuild changes them**. Re-run both scripts together (that is what `gis:build` does).

3. **Add the derived data** (each patches or adds files under `public/gis/`; rerun the first two after every `gis:build`, which rewrites `arcos.geojson`):

   ```bash
   .venv/bin/python scripts/add-repair-windows.py   # tags repaired ARCOS reports: repaired in the last 48 h / 30 days / earlier
   .venv/bin/python scripts/simulate-crew-status.py # SIMULATED crew status on open reports (reported / assigned / arrived / underway)
   .venv/bin/python scripts/build-roads.py          # interstates and busy roads from OpenStreetMap (Overpass) -> roads.json
   .venv/bin/pip install tifffile                    # needed once, for the next script
   .venv/bin/python scripts/build-canopy.py         # NLCD Tree Canopy Cover from MRLC -> canopy.bin / canopy.json
   ```

   - `add-repair-windows.py` measures the 48 h and 30 day windows back from the **latest date in the extract** (stored as `asOf` in `manifest.json`), not from today, because the data is a historical snapshot.
   - `simulate-crew-status.py` exists because the utility data has no dispatch or arrival information. It is seeded, so reruns give the same result. Replace it with real crew data when available.
   - `build-roads.py` and `build-canopy.py` download from public services (Overpass API, MRLC web coverage service) and need network access; the results are static files.

4. **Weather.** The wind model reads `data/weather/*_hourly.csv` (Open-Meteo historical hourly weather for 27 towns, 2022-09-24 to 2026-08-18, wind speed and gusts in km/h at 10 m; see `data/weather/manifest.json`). It is part of the dataset you are given, not generated by a script here.

## Network map (`/map.html`)

Left panel tabs: **Layers**, **Inspect**, **Issues**, **Data**.

- **Layers.** Every layer toggles on/off with Select all / Clear per section (Network, Sectionalizing devices, Impact, Emergency services). Each layer has attribute filters with live counts (phases, voltage, mounting, state, facility names...). Primary conductors are colored and sized by phase count; dashed = underground. Large layers (secondary, premises, poles) load on demand. Basemaps: Dark, Streets, Satellite. A circuit selector highlights and zooms to a whole circuit.
- **Equipment order.** Derived from `matched_upstream.txt`, not hard-coded: the equipment classes between a premise and the breaker (transformer, fuses, reclosers, sectionalizers, step transformers), how common each is, and the most common orderings. Click an ordering to highlight every transformer that follows it.
- **Inspect.** Click a premise, transformer, device, pole, conductor or damage report to see its attributes and connections: serving transformer, secondary network, and the numbered upstream equipment path (dashed line + highlighted primary route). Clicking a protective device shows how many transformers and premises are downstream.
- **ARCOS damage.** Reports are filterable by damage type and asset type. Each report shows **person-hours** (`src/map/labor.ts`): remove + install of the matching compatible units × the 4.5 indirect labor multiplier. Poles and transformers use size-group averages; wire is costed as splice/termination hardware; access and site adders are not applied. The mapping table at the top of that file is the place to adjust assumptions. Repaired reports get their own symbols and a **Repair status** filter under Layers > Impact: open (red triangle), repaired in the last 48 hours (green circle, for infant-mortality monitoring), repaired in the last 30 days (teal diamond, recent history for reliability engineers), and repaired earlier (small grey ring). The windows count back from the extract date, not today (see Data setup).
- **Likely materials.** Inspecting an ARCOS report also lists the parts a replace-in-kind repair would probably need (`src/map/materials.ts`), inferred from its damage type and asset type: pole, crossarm and hardware; fuse cutouts and links; recloser or switch; transformer, cutout, arrester and connectors; primary conductor with splices and dead-ends; secondary cable. Where a primary line is within 40 m it shows that line's conductor, voltage, phases and mounting. It is an estimate from the report, not a work order; the report has no span length, pole class or kVA.
- **Isolation plan.** For each report the build finds the device to open so the fewest customers lose power: the nearest closed fuse, recloser or switch between the damage and the source (direction comes from the matched upstream paths). Clicking a report draws a red "open here" marker, a dashed line to it, and highlights the de-energized transformers and premises. If nothing can sectionalize the damage, the card says the substation breaker is the only option. Back-feed from normally-open ties is not modelled.
- **Issues.** Pick damage reports (default: not yet repaired), then **Prioritize** to get a ranked list, exportable as CSV. Score = customers off ×1 + life-support customers ×50 + a hospital (400) / fire station (150) / ambulance (150) within 500 m of the damage or any de-energized transformer (×0.4 out to 1.5 km). Weights live in `src/map/priority.ts`. The list and ranking persist while you click through issues.
- **Debug.** *Show premise addresses* (Layers tab) adds the street address and location ID to a selected premise's attributes via the API. Off by default; premises are otherwise anonymous.

Premises on the map carry only an anonymous ID, service type and customer count. Names, addresses, premise numbers and meters are never written to `public/`.

## Client chat (`/client.html`)

1. The chat first asks for the customer's **service address**. The server (`GET /api/premises/search?q=`) matches it against `data/premise-addresses.json` and returns at most 8 results; the address list is never sent to the browser. The source data has no street suffixes or ZIP codes, so addresses read like `2347 Gardner, Elliston, VA`. The shapefile's own `address` field is empty for every record; addresses are assembled from `anno_strin` + `road_name` + `city`. The chosen premise is remembered in `localStorage`.
2. Quick actions: **Check my outage status** (open utility damage reports whose isolation would also cut this premise), **When will power return?** (a range of hours from now, derived from the repair work divided by a crew of 2 to 8; set `CREW_MIN`/`CREW_MAX` in `server/premises.ts`; shown with a **progress timeline**: reported, crew assigned, crew arrived, repairs under way, power restored), **Safety tips**, and **Get outage updates**. Crew progress is **simulated** (`scripts/simulate-crew-status.py`). With several open repairs the timeline shows the least advanced one.
   The bell icon (next to the bug icon) opens an **outage updates** form: an email address or US mobile number, plus an address search if no address has been chosen yet (`POST /api/premises/:pid/updates`). Sign-ups are stored in the `update_subscriptions` table of `data/outages.sqlite`; **nothing is sent yet**, so a sender (email/SMS service) still needs to be connected. The assistant offers updates once, under outage status replies, to customers who have an open outage and have not signed up. The map can be zoomed and panned (not rotated).
3. The bug icon opens debug options: include already-repaired outages (so the storm data shows results), and show location IDs. Both are off by default.

4. **Free-text questions** go to Groq (`POST /api/client-chat`, model from `GROQ_MODEL`; reasoning is hidden). The model is prompted to be a helpful power-outage assistant and is given the customer's own context (address, life-support flag, open damage reports, restoration estimate) so it never invents causes or times. It can't dispatch crews or change reports, and it sends 911 guidance for downed lines or medical urgency. Answers stream in as markdown. Requires `GROQ_API_KEY`.

Customers cannot file outage reports here.

**Satellite backdrop.** Three quarters of the page is plain satellite imagery (no network or circuit data). Choosing an address flies the map in to it and drops a pin; changing the premise flies back out.

**Before exposing this publicly:** the premise endpoints (`/api/premises/*`) have no authentication or rate limiting, so anyone who can reach the server can look up an address and learn its circuit and service type. Put them behind sign-in first. Restoration times are estimates from standard repair hours, not utility commitments. Crew progress is simulated, and outage-update sign-ups store contact details without sending anything yet.

## Outage risk

A color-coded band (none / low / moderate / high / severe) with a confidence indicator sits along the bottom of the client map. It is computed per premise by `assessRisk` in `server/premises.ts` and returned by `GET /api/premises/:pid/status` along with a `wind` detail object. The score is the sum of six factors worth 0-3 points each (0-18); the level is `none` when there is no open report affecting the premise or within 2 km, otherwise low (0-5), moderate (6-9), high (10-13), severe (14+).

| Factor | What it measures | Points |
| --- | --- | --- |
| Pole age | Mean age of poles within 150 m (install year). Poles 70 years or older, and placeholder dates (1901 or earlier), are ignored | <20 y: 0, <35: 1, <50: 2, 50+: 3 |
| Road exposure | Share of those poles within 25 m of an interstate/trunk road (weight 1) or a primary/secondary road (weight 0.5), from OpenStreetMap | none: 0, <10%: 1, <30%: 2, 30%+: 3 |
| Wind and trees | Structural wind load on the serving pole and transformer at the area's typical yearly peak gust, plus tree canopy around the nearby line | structural (0-3) + canopy (0-3), capped at 3 |
| Ice and wet ground | Radial ice from the worst freezing-rain event on record at the nearest weather town, plus a point for wooded lines where gusty days often find the ground already wet | ice, only in or near Dec-Mar: <6 mm: 0, <10: 1, <15: 2, 15+: 3; +1 if canopy 30%+ and 40%+ of gusty days are on wet ground; capped at 3 |
| Escalation | Customers cut by the outage, circuit-wide outage, life support at the address (+1) | <50: 0, <300: 1, <1500: 2, 1500+ or circuit-wide: 3 |
| Surrounding outages | Open damage reports within 2 km | 0: 0, 1-2: 1, 3-6: 2, 7+: 3 |

**Confidence** starts high and drops one step for each of: damage off the traced network (approximate reach), a circuit-wide assumption (no device isolates the damage), no pole age data nearby, no wind/equipment data, pole class/height/material assumed, or no canopy data. With no open report it is medium, since that does not rule out an unreported outage. The repair-time estimate is **not** part of the risk score (it is shown separately as "When will power return?").

### Wind loading (`server/wind.ts`)

A closed-form structural calculation, **not a trained model**. A physics-informed network or neural operator would need simulated or measured load data to train on, and none exists here; this calculation is what such a surrogate would approximate.

- **Equipment.** The serving transformer (rating, phases, mounting; e.g. `50 kVA XFR PL`, `ABC`, overhead) is matched to its pole by location id (20,301 of 20,303 overhead transformers match). Pole class, height and material come from the pole layer. Missing class defaults to class 5, missing height to 40 ft, and the confidence drops. Underground and pad-mounted (`PD`) equipment is not loaded by wind and scores 0.
- **Pole rating (ANSI O5.1-2022).** Wood pole classes carry a rated horizontal load applied 2 ft from the tip (class 1: 4,500 lb, 2: 3,700, 3: 3,000, 4: 2,400, 5: 1,900, 6: 1,500, 7: 1,200, 9: 740, 10: 370, H1-H6: 5,400-11,400 lb). Setting depth is 10% of the length + 2 ft. Capacity is that load times the lever arm from the groundline to 2 ft below the tip. Non-wood poles (fiberglass, steel, concrete, aluminium) use the same class table as an approximation, since O5.1 covers wood only.
- **Demand.** Wind pressure `0.00256 V^2` psf with the 10 m gust scaled to each height (power law, exponent 0.143), applied to: the primary wires (one per phase plus neutral), a secondary service cable, the transformer tanks (area from kVA) and the pole shaft (diameter from the class tip circumference and taper). Typical values, not measurements: 250 ft span, 0.5 in wire, 0.6 in service cable. Bending moments at the groundline are summed and divided by capacity.
- **Scoring.** Structural points follow NESC-style margins (2.5 load factor on wind, 0.65 strength factor): load below 13% of rated strength scores 0, below 19.5% scores 1, below 26% scores 2, otherwise 3.
- **Wind speed.** From the nearest weather town in `data/weather`: the scored gust is the mean of the yearly peak gusts (four 365-day windows). The record gust, the last 72 hours of data, and the pole's load at 50/70/90/110 km/h are also kept so the assistant can explain stronger gusts. The weather data is historical, so there is **no forecast**; the assistant says so and points customers to the National Weather Service.
- **Trees.** NLCD Tree Canopy Cover (USFS / MRLC, 2021, 30 m cells) is averaged over 3 x 3 cells around each pole within 150 m (`server/canopy.ts`; the grid is in EPSG:5070 and the lookup carries its own Albers projection). Under 15% canopy scores 0, under 30% scores 1, under 50% scores 2, otherwise 3. Canopy cover says how wooded the corridor is, not which trees are hazards: there is no tree height, health or trimming data.
- **Ice (`winterFactor`).** Freezing rain is rain at or below 0 C in the hourly files. Radial ice is accreted with the Jones (1998) simple freezing-rain model (rain flux plus wind-driven flux onto a cylinder; the diameter cancels out) and reset when it thaws. Ice only counts near ice season: the months holding at least 4% of all freezing-rain hours in the record (December to March) form the season, the ice points are scaled by how close the date is to it (full inside it, fading to nothing 30 days before and after), and the wet-ground point is not seasonal. Set `RISK_DATE=YYYY-MM-DD` when starting the server to preview another date, e.g. `RISK_DATE=2027-01-20 bun index.ts`; the assistant's "today" follows it. The worst event is kept per town (8-21 mm, about 0.3-0.85 in, for the Feb 2025, Jan 2025 and Jan 2026 storms; the Feb 2025 one matches the spike in ARCOS reports). The detail object also gives the pole's load with that ice on the wires and a 40 mph gust (an NESC heavy-loading style case). Underground and pad-mounted equipment scores 0.
- **Wet ground.** Soil wetness is an antecedent precipitation index: daily precipitation with 10% a day decay. Wet means the top quarter of the town's own history. The model keeps gusts of 45 mph or more per year and the share of those days on wet ground, as a stand-in for how easily trees uproot when strong wind arrives. There is no soil probe or soil-moisture data behind it.
- **Limits.** Only direct loading, canopy, ice on the wires and the wetness index are modelled. Ice on tree branches is not (it is described to the customer, not measured). Pole decay, conductor tension, guying, ice and terrain speed-up are not. Most real wind outages come from trees and branches on lines.

### Assistant behaviour

The client chat model (Groq) is given the risk level, each factor's plain-language label, the data caveats, the wind and canopy facts and the equipment serving the home. Asked why the risk is what it is, it answers with a one-sentence lead-in and a short bullet per factor (pole age, nearby roads, wind and trees, ice and wet ground, size of the outage, other outages nearby), with trees and gusts together in one bullet and ice and wet ground in its own, and no formulas or scores. It offers outage updates once to customers with an open outage.

### Standards and data sources

- ANSI O5.1-2022, Wood Poles: Specifications and Dimensions (class load ratings).
- NESC (IEEE C2) strength and load factors, used for the scoring margins; wind pressure form from ASCE 7.
- NLCD Tree Canopy Cover, USFS / MRLC (https://www.mrlc.gov): canopy percent, 2021 release.
- OpenStreetMap contributors via the Overpass API: road classes (ODbL). Road class stands in for traffic; there are no traffic counts.
- Open-Meteo Historical Weather API (https://open-meteo.com, CC BY 4.0): gridded reanalysis, not station observations; temperature, rain and precipitation also drive the ice and wet-ground estimates.
- Jones, K. F., 1998, "A simple model for freezing rain ice loads", Atmospheric Research 46: radial ice on a cylinder from rain flux and wind.
- AEP shapefiles (Data1, Data2, matched_upstream): network, poles (class, height, material, install year), transformers and ARCOS damage reports.
- Compatible-unit (CU) hour tables supplied for this project (`src/map/labor.ts`): repair person-hours and the 4.5 indirect labor multiplier.

## Chat app (`/`)

Users and Workers have separate conversations (kept in memory while the page is open). Chat tools let users report outages and find nearby community reports, and let workers mark reports resolved. Bun's built-in SQLite stores reports in `data/outages.sqlite` (override with `DATABASE_PATH`); the database is created on startup. Outage prediction and official utility status are not implemented.

Supply an address/place name or latitude/longitude in chat. Place names are geocoded through OpenStreetMap Nominatim; ambiguous matches require clarification. The assistant asks for confirmation before submitting or resolving reports. Nearby searches default to 25 km (maximum 200 km), return up to 100 nearest reports, and exclude resolved reports unless requested in worker mode. Do not include private details in reports: they are visible to other users through searches.

Nominatim's public endpoint is intended for light prototype use; production should use a geocoding service with appropriate capacity and usage controls.

The interface tabs are presentation only, not authentication or role-based access control. The server only exposes the resolution tool in worker mode, but anyone can select that mode. Add authenticated worker roles before exposing this prototype publicly. Mutation confirmation is enforced through assistant instructions, not a separate authorization boundary.
